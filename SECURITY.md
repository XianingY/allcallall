# Security Policy

## Supported Versions

Only the latest main branch is currently receiving security updates.

| Version | Supported          |
| ------- | ------------------ |
| `main`  | :white_check_mark: |
| < 1.0.0 | :x:                |

## Scope

**In scope**

- `backend/` — Go API, authentication, tenant isolation, webhook handling
- `web/`, `mobile/`, `desktop/` — clients, token storage, transport security
- `infra/` — Compose / Kubernetes / Helm manifests, WAF and TLS configuration shipped in this repository
- CI workflows and release tooling under `.github/`

**Out of scope**

- Findings that require a compromised end-user device or a malicious browser extension
- Denial of service caused purely by volumetric traffic (report the design concern instead)
- Vulnerabilities in third-party dependencies already publicly disclosed upstream —
  open an issue or PR to bump the dependency instead
- Reports generated by automated scanners without a demonstrable impact
- Self-hosted deployments running unpatched forks or default credentials

## Severity Classification

Reports are triaged with the rubric below; severity drives the remediation target.

| Severity | Definition | Examples |
| -------- | ---------- | -------- |
| Critical | Remote exploitation with no authentication, or cross-tenant data access at scale | Authentication bypass, tenant isolation break exposing another organization's messages or recordings, RCE on the API |
| High | Privilege escalation, or sensitive data exposure requiring authentication | Broken access control on an admin endpoint, stored XSS in message rendering, secret disclosure through logs |
| Medium | Meaningful weakening of a control, or limited data exposure | Missing rate limit on an authentication endpoint, IDOR limited to non-sensitive fields, CSRF on a state-changing route |
| Low | Hardening gaps with no direct exploit path | Verbose error messages, missing security headers on static assets, outdated-but-unexploitable dependency |

## Reporting a Vulnerability

If you discover a security vulnerability within AllCallAll, please send an e-mail to security@allcallall.com. All security vulnerabilities will be promptly addressed.

Please do not report security vulnerabilities through public GitHub issues.

To speed up triage, include:

- The affected component and commit SHA
- A step-by-step reproduction (a script or request capture is ideal)
- The impact you believe is achievable, plus any preconditions (authentication level, tenant, feature flags)

## Disclosure Timeline

| Stage | Target |
| ----- | ------ |
| Acknowledgement | Within **3 business days** of receipt |
| Initial assessment and severity assignment | Within **7 days** |
| Fix merged | Critical: **7 days** · High: **30 days** · Medium: **90 days** · Low: best effort |
| Coordinated public disclosure | **90 days** after the fix is released, or earlier by mutual agreement |

If a target cannot be met we will say why and agree on a revised date rather than going silent.
We credit reporters in the release notes unless they prefer to stay anonymous.

## Safe Harbor

We will not pursue legal action against researchers who:

- Report findings in good faith through the channel above
- Avoid privacy violations, service degradation, and data destruction while testing
- Give us a reasonable window to remediate before public disclosure
